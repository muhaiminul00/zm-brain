## Problem Statement

ZeroManual (product name; ZM-Brain is the underlying engine; "Company Brain" is
the product category, not the name) completed a full theoretical grounding
phase — eight canonical docs mapping the maximum-ceiling enterprise vision,
frozen July 2026, zero implementation. This session starts the actual
Technical Architecture/Building phase, deliberately narrowed: D2C (not
B2B/enterprise), targeting individual developers/builders running multiple
LLM & agent tools, wedge = proper context sync (project/entity awareness fed
across tools), low-cost. Strategy: ship the narrow slice properly, get real
paying customers, then broaden back toward the fuller canonical vision.

## Status Quo

Developers cobble together fragmented tooling: open-source stores like
gbrain and Obsidian for preserving context, plus ad-hoc memory files and
manual re-context per tool. These only work where the target tool exposes an
extensibility surface (hooks/MCP/plugins) — closed tools get no benefit,
forcing avoidance or manual re-explaining. No measured time-cost yet; the
founder's own dev-community observation is the only signal.

## Target User & Narrowest Wedge

Target (self-as-persona, still not independently named): a developer running
multiple LLM/agent tools of varying openness — some with hook/plugin/MCP
support, some without — who currently duct-tapes context continuity for the
supported tools and eats a real cost (redone work, missed details, wrong
agent decisions) on the unsupported ones.

The sharpest signal from the session: *"first think how to tell it the full
story"* — the pain is not memory loss per se, it's the cognitive tax of
deciding what context matters and reconstructing it before every tool
switch.

Wedge (confirmed, not a storage backend competing with the ~196 existing
memory MCP servers or Anthropic's own native memory beta): a central
capture/process/store layer — plain, readable/editable/versionable wiki-style
files, not a vector-RAG store — that feeds context out to wherever the
developer is working, through whatever channel that destination tool
actually allows (native MCP/hook integration where supported, a
manual-paste-ready export where not).

- D2C only for v1 — no enterprise/team features, no email/calendar
  ingestion, no agent autonomy.
- Low-cost — priced for an individual developer to pay out of pocket. No
  number or comparator has been set (open — needs founder input, not a
  guess this doc should invent). This is in direct tension with cross-device
  sync — hosted sync infrastructure costs money to run.
  **Superseded at `/plan-eng-review` (2026-09-02) — this default did NOT
  hold.** The paragraph below was this doc's original recommendation
  (local-only/no hosted relay); it was overridden by the "Technical
  Architecture Lock-In" section's Finding 1/2 (Supabase + a hosted MCP
  server, both real recurring costs, both required once Claude.ai web chat
  delivery was locked). Left here, struck through in spirit, so a reader
  who stops at Constraints doesn't get a stale picture: ~~local-only / P2P
  sync on a free or low tier for v1; a hosted relay, if ever needed, sits
  behind a future paid tier rather than being assumed into the low-cost
  baseline~~. The low-cost/hosted-infra tension is now genuinely
  unresolved, not resolved-by-default — see Unresolved Decisions (pricing)
  at the end of this doc.
- Store design must be files-first (readable/editable/versionable), not
  opaque embeddings — this is both a differentiation point (landscape
  research found "opacity and trust" as the most-cited failure mode of
  existing memory MCP servers) and consistent with the founder's own
  already-validated `project-memory` design.
- **BLOCKING — data sensitivity:** the store will hold project context that
  may include secrets or business detail. No encryption-at-rest/in-transit
  or local-only-vs-hosted-relay trust model has been decided. This must be
  resolved *before* the sync-mechanism decision (Open Questions) — sync's

## Approaches Considered

**Effort/Risk scale:** S = &lt;1 week, M = 1-2 weeks, L = 2-6 weeks, XL = 6+
weeks (rough, CC-assisted estimate, not a committed schedule). Risk = chance
the approach either doesn't ship on that timeline or ships something nobody
validated wanting.

### Approach A: Minimal Viable — Wiki-Store Packer
Local file-based store (`.zeromanual/`, wiki-style markdown, generalizing the
founder's own `project-memory` plugin) + a pack/deliver command that
assembles paste-ready context and pushes it via whatever channel the
destination tool allows. Effort S/M, Risk Low. Rejected as the sole v1
scope — see Recommended Approach.

### Approach B: Ideal Architecture — ZM-Brain Core + Sync + Multi-Channel
A local-first core service implementing the "smart memory system": wiki
store + **[BLOCKING, not yet implementable as written] light hybrid
retrieval** (mechanism TBD — see Open Questions) + adapters (candidates,
sequencing TBD — see Open Questions/Distribution Plan: MCP server, CLI,
browser extension) + cross-device sync (conflict-resolution mechanism TBD,
default direction: local-only/P2P for v1 — see Constraints). Note: this
description is storage/sync-heavy relative to how thin the delivery-channel
side is specified — that imbalance is real, not just a drafting gap; the
stated wedge is delivery-out, but the selected build over-indexes on
store/sync.

**Write-governance/provenance (scoped down from the canonical Memory Model
doc) is DEFERRED OUT of this v1 scope by default**, not included — the
doc's own Open Questions found no articulated justification for it in a
single-user product (the user is the sole author of their own memory), and
including an unjustified enterprise-vision concept in a deliberately
narrowed v1 is scope creep on top of the already-flagged B-vs-A scope
tension. Restore it only if a specific single-user justification surfaces
at `/plan-eng-review`.

**Per-subsystem effort (replacing the single blended L/XL estimate — that
number understated the true cost of five independently substantial
subsystems bundled together):**
- Wiki store (files, generalizing `project-memory`): S
- Retrieval (mechanism TBD, likely keyword-only for v1 per Premise 3's
  files-first stance): S/M once decided, unscoped until then
- Sync + conflict resolution (git-backed store, last-write-wins, or
  app-level merge — pick one): M/L on its own
- CLI + MCP adapter: S/M
- Browser extension: M (store review cycles add calendar time beyond build
  time)
- Governance: 0 (deferred, see above)

Risk Med-High even with governance removed — sync + retrieval are still the
two subsystems most likely to blow the original L/XL estimate.

### Approach C: Creative/Lateral — Passive Capture, Browser-First
Flips the order: a browser extension/clipboard watcher passively builds the
wiki store as a byproduct of normal tool use, no explicit capture step,
attacking the "cognitive tax" pain most directly. Effort M, Risk Med
(passive-capture accuracy, privacy/consent model). Not selected — noted here
in case the delivery-side UX gets revisited later.

## Success Criteria

- A developer other than the founder uses ZM-Brain to avoid re-explaining
  project context when switching tools, without prompting.
- At least one non-founder user reports (unprompted) that losing access to
  it would cost them real time or rework.
- Core store stays inspectable — a user can open, read, and edit the
  underlying files directly, matching the differentiation bet against
  opaque memory backends.
- **Sync is built to spike/prototype quality for v1, not production
  quality** — it is explicitly excluded from v1 success measurement (it's
  the highest-risk, least-validated part of the remaining scope), so effort
  invested in it should match that bar, not a production SLA. Do not claim
  v1 "succeeded" based on sync working reliably; it needs its own criteria
  once conflict-resolution is resolved (see Open Questions).
- Write-governance is deferred out of v1 scope entirely (see Approach B) —
  no success criterion needed for something not being built.

### Architecture Findings (locked)

1. **MCP delivery vs. local-only default (confidence 8/10).** Claude.ai web
   chat's custom MCP connectors connect from Anthropic's cloud, not the
   user's machine — a local-only MCP server is unreachable from web chat.
   **Locked: add a hosted layer** (superseded by Finding 2's Supabase
   choice + the hosted-MCP-server gap in Cross-Model Tension 1 below) rather
   than dropping web chat from v1 delivery.
2. **Store backend (confidence 7/10).** Considered a Hostinger VPS
   pure-tunnel/proxy, a VPS-held copy, Supabase, Supabase+Pinecone, and
   Notion-as-store. **Locked: Supabase (hosted Postgres + pgvector) as the
   synced retrieval index; local git-backed markdown remains the source of
   truth** — directly reuses GBrain's own proven split
   (`docs/technical/Technical_Phase_GBrain_Reference_Note.md` §2-3: "Markdown
   files in a git repo = source of truth... Synced into Postgres for
   retrieval"), gets built-in RLS/auth/encryption-at-rest instead of custom
   VPS security work, and is always-on (solves Finding 1's availability
   need). Pinecone rejected as redundant with pgvector; Notion rejected as
   contradicting the files-first differentiation bet.
3. **Retrieval depth (confidence 7/10).** Reviewer recommended sequencing
   vector+BM25+RRF now, deferring graph traversal + cross-encoder reranker
   to v2 (GBrain's own benchmarks show smaller incremental gains from those
   two). **Founder locked the full GBrain stack for v1**: vector
   (pgvector/HNSW) + BM25 + RRF + graph traversal (regex-based, zero LLM) +
   cross-encoder reranker (GBrain uses a paid third-party API, ZeroEntropy,
   for this — a real recurring cost against the "low-cost" constraint, not
   yet priced). This directly resolves the design doc's BLOCKING "light
   hybrid retrieval" Open Question — no longer light, no longer TBD.
4. **Conflict resolution (confidence 7/10).** Reviewer recommended standard
   git merge conflicts (zero new code, current 2026 practice for personal
   git-backed markdown sync per web search). **Founder locked CRDT-based
   auto-merge instead.** Follow-up research found Automerge specifically
   recommended for "git-for-documents"-flavored products (a good fit) —
   correcting the reviewer's initial overstated "CRDT libraries are
   immature" framing — but flagged that markdown+YAML-frontmatter files need
   an explicit schema mapping (frontmatter as an Automerge map, body as
   Automerge Text) before CRDT applies; this mapping is Implementation Task
   T3 below, not yet designed. This directly resolves the design doc's
   Conflict Resolution Open Question.

### Cross-Model Tensions (Codex outside voice)

Codex's full review is preserved verbatim in this review's session log; the
two tensions below were put to the founder individually. Codex's other
points (full-scope-bias pattern, pricing/unit economics, delivery-surface
equivalence, competitive-copy risk, architecture-vs-product-leverage) are
folded into Unresolved Decisions and Implementation Tasks below rather than
each getting a separate gate — see those sections.

1. **MCP hosting gap (confidence 9/10, missed by the in-session review).**
   Codex: "Supabase does not replace a hosted MCP server... Postgres +
   pgvector is storage, not the connector service." Finding 2 above decided
   *where data lives*, not *what serves the MCP protocol to Claude.ai's
   cloud*. **Locked: build a small hosted MCP server** (Supabase Edge
   Function, or a lightweight compute-only process — no data storage — on
   the Hostinger VPS considered in Finding 1) that implements MCP and
   queries Supabase for retrieval. Needs its own auth before public
   exposure — see Implementation Task T6.
2. **Write-path authority (confidence 8/10).** Codex: "Git-backed markdown
   is source of truth conflicts with Supabase retrieval index, CRDT state,
   cloud MCP reads, and possible remote writes unless there is one
   authoritative write path." **Locked: local git markdown is the only
   human/agent write surface; Supabase is a read-only derived view, rebuilt
   from git on sync — never a second source of truth.** Founder's
   refinement: the git→Supabase propagation must be part of the same write
   operation (not a lagging batch job), so a write is "done" only once both
   the markdown file and the Supabase index reflect it — see Implementation
   Task T2. Any write coming in through the hosted MCP server (an agent
   writing via Claude.ai web chat, say) must round-trip back to the local
   git repo, not write Supabase directly — that round-trip mechanism is not
   yet designed (Implementation Task T2 also covers this).

### Data flow (locked write/read path)

```
WRITE PATH (single authority: local git markdown)
  human/local agent edit
```

### Failure Modes

| # | Failure | Test? | Error handling? | User sees |
|---|---|---|---|---|
| FM1 | Hosted MCP server queries Supabase mid-sync (race between git→Supabase push and a concurrent read) | No | Not designed | **Silent** — stale/partial read, no indication — CRITICAL GAP |
| FM2 | CRDT auto-merge produces a valid Automerge state but a messy/unexpected markdown diff the user didn't make by hand | No | Not designed | Silent trust erosion in the "inspectable markdown" bet (Codex) |
| FM3 | Reranker API (ZeroEntropy) call times out or errors mid-retrieval | No | Not designed | Unclear — does the query fail entirely, or degrade to non-reranked results? |
| FM4 | A captured file contains a real secret (API key, credential) before T4 (redaction) is built | No | Not designed | **Silent** — secret propagates to Supabase (third-party) and any LLM reading it as context — CRITICAL GAP, highest severity of the four |
| FM5 | A secret already captured before T4 exists is baked into git history (append-only) and, once T2/T3 sync, propagated to every synced device and rebuilt Supabase mirror | No | Not designed | **Silent, and worse than FM4 implies** — a later redaction only removes it from HEAD; the secret must be treated as compromised and rotated, not just redacted going forward (Claude adversarial pass, `/ship`) |
| FM6 | Captured content contains adversarial instructions ("ignore previous instructions", fake policy) or link/heading spam designed to bias graph traversal and RRF ranking | No | Not designed | **Silent** — no instruction/data separation, trust labels, or retrieval sanitization specified anywhere in the stack; a pasted README or web page becomes a direct agent-compromise or context-poisoning path — CRITICAL GAP (Codex adversarial pass, `/ship`) |
| FM7 | Reranker API (ZeroEntropy, third-party) receives candidate context on every remote retrieval call, with no processor boundary, opt-out, redaction-before-rerank, or logging policy specified | No | Not designed | **Silent** — project memory (may include secrets/proprietary code/customer data) leaves the trust boundary the data-sensitivity section describes as Supabase/hosted-relay-only; the reranker itself is an unacknowledged exfiltration path (Codex adversarial pass, `/ship`) |
| FM8 | CRDT auto-merge on concurrent edits produces syntactically valid markdown that is semantically wrong (duplicated headings, split code fences, corrupted YAML scalar styles, reordered frontmatter, broken links) | No | Not designed | Silent — "valid markdown" is not the same as "correct memory"; a user trusts the file as ground truth without knowing the merge silently reshaped it (Codex adversarial pass, `/ship`) |

FM1, FM4, FM6, and FM7 are flagged as the highest-severity **critical
gaps**: no test, no error handling, and the failure would be silent, and
(FM6/FM7 specifically) touch security/privacy boundaries the doc otherwise
claims to have addressed. FM1/FM4 are covered by Implementation Tasks
already listed above (T2 for FM1, T4 for FM4) — the gap is that T2/T4 don't
yet specify the failure-mode behavior itself (what happens on a race, what
counts as a secret), only that the mechanism must exist. **FM5, FM6, FM7,
and FM8 have no Implementation Task at all yet** — they were surfaced by
the two adversarial-review passes at `/ship` (2026-09-02), after
Implementation Tasks were already written, and are recorded here as newly
discovered scope, not yet triaged into T1-T8's numbering. Two related gaps
also surfaced but are process/design questions rather than failure modes:
deletion/tombstones (T3/T4/T6) aren't connected to Supabase, reranker logs,
git history, or backups — no actual erasure semantics exist despite
provenance being tracked; and derived Supabase rows have no version/
freshness contract (no generation number, source commit SHA, or
indexed-at timestamp), so a stale row can be served with full confidence.
Both are folded into Unresolved Decisions below rather than given their
own FM numbers, since they're gaps in a mechanism's *design* rather than
a specific failure trigger.

### Worktree Parallelization Strategy

| Step | Modules touched | Depends on |
|------|------------------|------------|
| Wiki store + git write path (T2 partial) | store/ | — |
| CRDT/Automerge schema mapping (T3) | store/ | Wiki store's file format |
| Supabase schema + sync pipeline (T2 partial) | sync/ | Wiki store's file format |
| Capture provenance tagging (T7) | store/, sync/ | Wiki store's file format |
| Secrets/redaction pass (T4) | capture/ | Wiki store's file format |
| Hosted MCP server (T1) | server/ | Supabase schema (queries it) |
| RLS/auth policy (T6) | server/, sync/ | Supabase schema, hosted MCP server |
| Retrieval stack: vector+BM25+RRF+graph+reranker | retrieval/ | Supabase schema populated |
| Source-adapter event model (T5) | adapters/ | Wiki store's file format |

**Lane A (foundational, sequential):** Wiki store + git write path → CRDT
schema mapping. Nothing else can start until the file format is frozen.

**Lane B (parallel once Lane A's file format lands):** Supabase schema/sync
pipeline, capture provenance tagging, secrets/redaction pass, source-adapter
event model — none of these four share a module directory, and none depend
on each other, only on Lane A. **Build-order caveat (Claude adversarial
pass, `/ship`): "parallel to build" does not mean "parallel to enable
against real data."** The Supabase sync pipeline must not be turned on
against non-test data until the secrets/redaction pass (T4) is actually
merged — otherwise the normal execution of this plan ships FM4/FM5 (a
secret syncing to Supabase and permanently into git history) by
construction, not by exception.

**Lane C (sequential after Lane B's Supabase schema):** Hosted MCP server →
RLS/auth policy (same module, sequential) → retrieval stack (needs the
schema populated to test against).

**Execution order:** Launch Lane A alone first (nothing else can safely
start). Once the file format is frozen, launch the four Lane B workstreams
in parallel worktrees. Merge all four. Then Lane C sequentially.

**Conflict flag:** none of the parallel Lane B workstreams touch a shared
module directory — no merge-conflict risk between them.

### Unresolved decisions that may bite you later

- **No kill-rule for The Assignment.** Founder explicitly chose to leave
  this unresolved (Cross-Model Tension 3, option C) after the reviewer
  named the risk directly: with scope already locked full-B regardless of
  what The Assignment shows, the observation is not currently load-bearing
  on any build decision. Not re-argued per this review's own rules — noted
  here so it isn't silently forgotten.
- **Full-scope-bias pattern (Codex, confidence not scored — a pattern
  observation, not a single finding).** Every phased-vs-full choice in this
  review (Approach B, retrieval depth, conflict resolution, and originally
  the hosted-relay-vs-tunnel choice) was resolved toward the fuller option.
  Individually each was defended or accepted with reasoning; the pattern
  itself was surfaced to the founder but not gated on a single decision —
  recorded here as a standing risk to watch, not something this review
  reversed.
- **Pricing / unit economics.** Still no number. Now demonstrably more
  urgent than when the design doc was written — Supabase, the reranker API,
  and the hosted MCP server are all real recurring costs the original
  "local-only, no hosted relay" default was specifically written to avoid.
  "Low-cost D2C" is not yet substantiated (Codex).
- **Delivery-surface equivalence.** "MCP/plugin-based, testable against
  Claude Code + Claude.ai web chat + OpenAI where feasible" was locked as
  one phrase but names three surfaces with different integration contracts
  (Codex). Each needs its own concrete spec before "testable" is actually
  true for all three — not done in this review.
- **Competitive differentiation vs. Supermemory / Second Brain for AI**
  (already an open question in the Competitive Landscape section) —
  unchanged by this review; if anything sharper now, since Codex notes
  those competitors "can copy visible UX faster than ZeroManual can finish
  deep infrastructure" — the full-scope build path is slower to reach
  parity-plus-differentiation than a narrower one would have been.
- **No erasure semantics.** (Codex adversarial pass, `/ship`.) Provenance
  answers "where did this come from" (T7), but nothing answers "how does a
  deleted/redacted fact actually disappear" — git history, CRDT tombstones
  (T3), Supabase rows, embeddings, BM25 index entries, reranker request
  logs, and backups can all independently retain what the user believed was
  deleted. This is both a privacy gap and a retrieval-correctness gap (a
  "deleted" fact can still be retrieved from a stale index).
- **No freshness/version contract on the Supabase mirror.** (Codex
  adversarial pass, `/ship`.) "Supabase is a read-only derived view" has no
  mechanism attached — no generation number, source commit SHA, per-
  document version, or indexed-at timestamp. A remote MCP client (Claude.ai
  web chat, OpenAI) can be served stale context with full confidence and no
  way to detect it. Related to FM1, but a design gap rather than a race
  condition — even a perfectly reliable sync still needs this to let a
  reader know how fresh what they got actually is.
- **Read-only Supabase needs writes to exist.** (Codex adversarial pass,
  `/ship`.) The store-backend decision calls Supabase "read-only," but
  indexing (embeddings, BM25, graph edges, ranking metadata) requires the
  hosted MCP server to write to it. The doc needs to distinguish
  user-writes (forbidden, per the write-path-authority decision) from
  system-writes (required for indexing) before T6's RLS policy can actually
  be written correctly — right now "read-only" and "needs system writes"
  read as contradictory.
- **RLS may be decorative depending on the credential model.** (Both
  adversarial passes, `/ship` — Claude's and Codex's readings converge.) T6
  says "write the RLS policy as if it weren't single-user," but nothing
  specifies whether the hosted MCP server authenticates to Supabase with a
  per-caller identity (RLS actually gates something) or one shared
  service-role key (RLS gates nothing — the server bypasses it by design).
  This is a founder/architecture decision, not a documentation fix.
- **Original "non-extensible tool" pain isn't concretely solved by locked
  v1 delivery.** (Codex adversarial pass, `/ship`.) The Problem Statement's
  sharpest pain point names tools with no extensibility surface at all;
  locked v1 delivery is MCP/plugin-only (Claude Code, Claude.ai web chat,
  OpenAI). The "manual-paste-ready export" fallback from the original Wedge
  section is still named as the answer for closed tools, but isn't
  concretely specified anywhere in what's now locked — see the Browser
  extension delivery channel TODO.
